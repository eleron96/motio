# API пространства

У Motio есть небольшой HTTP API для других систем. Он умеет две вещи:

- **Читать пространство**: люди, проекты, задачи, вехи и отсутствия — для
  отчётов, дашбордов и выгрузок в инструменты, которыми ваша компания уже
  пользуется.
- **Импортировать отсутствия** (отпуск, больничный, обучение, выходные) из
  системы, где компания их ведёт: учёт времени, HR, расчёт зарплаты.
  Импортированные отсутствия ведут себя точно так же, как введённые вручную:
  закрашивают дни на таймлайне, выталкивают из них задачи человека и учитываются в
  тепловой карте загрузки.

Создавать и менять задачи, проекты, вехи и людей API не может.

Те же данные может читать ИИ-ассистент — через встроенный
[MCP-сервер](mcp.md), с тем же токеном.

## Как включить

1. Образ `web` собирается с `VITE_FEATURE_WORKSPACE_API=true` (см.
   [Configuration](../configuration.md#feature-flags)). Без этого раздел в
   настройках скрыт; сам адрес API существует в любом случае, но требует токен.
2. Администратор пространства открывает **Настройки рабочего пространства → API →
   Создать токен**, называет его по имени системы, которая будет им пользоваться,
   выбирает, что он может (см. [Области](#области)), и копирует токен. Он
   показывается **один раз**; Motio хранит только его хеш SHA-256.
3. Токен записывается в настройки другой системы как секрет.

У пространства может быть до 10 действующих токенов. **Отозвать** отключает токен
сразу; импортированные им отсутствия остаются.

## Области

Что может токен, выбирается при создании и потом не меняется: чтобы дать системе
больше или меньше, создайте новый токен и отзовите старый.

| Область | В настройках | Что открывает |
|---|---|---|
| `read` | Чтение пространства | все методы `GET` ниже; ничего не меняет |
| `time_off` | Импорт отсутствий | `GET`, `PUT` и `DELETE` для `/time-off` |

У токена может быть одна область или обе. Запрос за пределами его областей
получает `403` (`forbidden`). У токенов, созданных до появления областей, есть
только `time_off`: они продолжают делать ровно то, что делали.

## Основное

| | |
|---|---|
| Базовый адрес | `https://<ваш адрес Motio>/functions/v1/api/v1` |
| Авторизация | `Authorization: Bearer motio_…` |
| Формат | JSON на входе и на выходе, UTF-8 |
| Лимит запросов | 5 запросов в секунду с одного IP, всплеск до 20; сверх этого `429` |
| Размер запроса | до 256 КБ и 500 элементов в запросе |
| Идентификаторы | UUID |
| Даты | `YYYY-MM-DD` |
| Отметки времени | ISO 8601 в UTC с явным смещением и до шести знаков после запятой: `2026-10-28T09:12:44.512+00:00`, `2026-09-19T15:08:16.800568+00:00` |

API рассчитан на серверы и скрипты. Заголовков CORS он не отдаёт, поэтому страница
в браузере обратиться к нему не может — заодно токен не попадает в браузеры.

Токен принадлежит одному пространству, и каждый метод отвечает только за него:
назвать другое пространство нельзя никак.

Параметры запроса, которых метод не знает, игнорируются, а из повторённого
параметра берётся первое значение: если фильтр как будто не действует, проверьте,
правильно ли он написан.

### Страницы

`GET /tasks` и `GET /milestones` отдают по одной странице: `limit` элементов (по
умолчанию 200, максимум 500) и `next_cursor`. Передайте его обратно как `cursor`,
с теми же фильтрами, чтобы получить следующую страницу; на последней `next_cursor`
равен `null`. Остальные списки короткие и приходят целиком.

```bash
curl -s "https://planner.example.com/functions/v1/api/v1/tasks?limit=500&cursor=$NEXT_CURSOR" \
  -H "Authorization: Bearer $MOTIO_TOKEN"
```

### Как сопоставляются люди

Отсутствие привязывается к человеку по **почте** — почте его учётной записи
Motio, без учёта регистра. Человек должен быть участником пространства. Людей на
таймлайне без учётной записи (внешних) сопоставить нельзя: для них вернётся
`PERSON_NOT_FOUND`.

### Что API может трогать

У каждой записи, которую вы отправляете, есть `external_id` — идентификатор
отсутствия в вашей системе (до 200 символов, уникален в пределах пространства).
API создаёт и обновляет записи **по этому идентификатору** и удаляет только те, у
которых он есть. У отсутствий, введённых в Motio вручную, `external_id` нет; API
их никогда не меняет и не удаляет.

У одного человека не может быть двух пересекающихся отсутствий. Если
импортируемый период пересекается с существующим (импортированным или введённым
вручную), этот элемент отклоняется с `OVERLAP`; ничего не объединяется и не
перезаписывается.

Если кто-то отредактирует импортированное отсутствие в Motio, следующий импорт с
тем же `external_id` перезапишет правку: источником истины остаётся ваша система.

## Чтение пространства

Всем методам этого раздела нужна область `read`.

### Пространство

```
GET /workspace
```

```json
{"id": "8d2f6c1e-…", "name": "Studio North"}
```

Простой способ проверить, что токен работает и какому пространству он
принадлежит.

### Люди

```
GET /members
```

Все, кто есть на таймлайне: участники с учётной записью и люди, добавленные без
неё.

```json
{
  "items": [
    {
      "id": "5b7e0d11-…",
      "name": "Anna Becker",
      "email": "anna@example.com",
      "role": "editor",
      "group": "Design",
      "has_account": true,
      "is_active": true,
      "deactivated_at": null
    }
  ]
}
```

`id` — то, что задачи несут в `assignee_ids`. `email` и `role` (`admin`, `editor`,
`viewer`) берутся из учётной записи человека, пока она состоит в пространстве. Они
равны `null` у людей без учётной записи и у тех, кто вышел из пространства, но
остался строкой на таймлайне (`has_account` при этом остаётся `true`). `group`
равен `null`, если человек не состоит ни в одной группе. `is_active` равен `false`
у того, кого убрали с таймлайна; в `deactivated_at` лежит момент, когда Motio это
записал, и он может быть `null`.

### Проекты

```
GET /projects?archived=true|false
```

Без `archived` отдаются и действующие, и архивные проекты.

```json
{
  "items": [
    {
      "id": "c41a9e70-…",
      "name": "Harbour bridge",
      "code": "HB",
      "color": "#3b82f6",
      "status": "In progress",
      "archived": false,
      "customer_id": "0e6b2a4d-…",
      "customer": "North",
      "created_at": "2026-09-02T08:15:00.000000+00:00"
    }
  ]
}
```

`status` — статус в свободной форме из карточки проекта; `code`, `status` и клиент
равны `null`, если не заданы.

### Задачи

```
GET /tasks?from=YYYY-MM-DD&to=YYYY-MM-DD&project_id=…&assignee_id=…&updated_since=…&limit=…&cursor=…
```

Все фильтры необязательны:

| Фильтр | Что выбирает |
|---|---|
| `from`, `to` | задачи, которые пересекаются с диапазоном (можно указать только одну границу) |
| `project_id` | задачи одного проекта |
| `assignee_id` | задачи, назначенные одному человеку (`id` из `/members`) |
| `updated_since` | задачи, изменённые в этот момент или позже, например `2026-11-01T09:00:00Z`; часовой пояс обязателен. Значение `updated_at` из ответа можно отправить обратно как есть, вместе с микросекундами, — только закодируйте в адресе `+` как `%2B` |

Задачи идут по дате начала, [по одной странице](#страницы):

```json
{
  "items": [
    {
      "id": "3f0c7a52-…",
      "title": "Structural review",
      "project_id": "c41a9e70-…",
      "assignee_ids": ["5b7e0d11-…"],
      "start_date": "2026-11-09",
      "end_date": "2026-11-13",
      "status_id": "9a1d4c02-…",
      "status": "In progress",
      "is_done": false,
      "is_cancelled": false,
      "type": "Review",
      "priority": "high",
      "tags": ["urgent"],
      "repeat_id": null,
      "created_at": "2026-10-28T09:12:44.512000+00:00",
      "updated_at": "2026-11-03T14:02:10.090000+00:00"
    }
  ],
  "next_cursor": null
}
```

`end_date` — последний день задачи, включительно. `status` и `type` — названия из
настроек пространства; `is_done` и `is_cancelled` говорят, что статус означает,
как бы он ни назывался: у выполненной задачи `is_done`, у отменённой —
`is_cancelled`, но не `is_done`, у всех остальных — ни то, ни другое. `priority`
равен `low`, `medium`, `high` или `null`. У задач одной повторяющейся серии общий
`repeat_id`. `project_id` равен `null` у задачи без проекта, `assignee_ids` пуст у
задачи без исполнителя.

Удалённая задача просто перестаёт появляться: чтобы зеркалить задачи в другой
системе, сравнивайте идентификаторы, а не полагайтесь только на `updated_since`.

### Одна задача

```
GET /tasks/{id}
```

Те же поля плюс описание и чек-лист:

```json
{
  "id": "3f0c7a52-…",
  "title": "Structural review",
  "description": "<p>Check the drawings against the survey.</p>",
  "subtasks": [
    {"title": "Check the drawings", "is_done": true},
    {"title": "Write up findings", "is_done": false}
  ]
}
```

`description` — HTML в том виде, как он написан в карточке задачи, или `null`.
`404`, если в пространстве нет задачи с таким идентификатором. Комментарии и
вложения в API не входят.

### Вехи

```
GET /milestones?from=YYYY-MM-DD&to=YYYY-MM-DD&project_id=…&limit=…&cursor=…
```

По дате, [по одной странице](#страницы):

```json
{
  "items": [
    {
      "id": "71c5e9aa-…",
      "project_id": "c41a9e70-…",
      "date": "2026-11-20",
      "title": "Handover",
      "note": null,
      "status": null,
      "include_in_workload": false,
      "updated_at": "2026-10-30T11:40:00.000000+00:00"
    }
  ],
  "next_cursor": null
}
```

`status` равен `done`, `current` или `upcoming`, если кто-то задал его вручную, и
`null`, если Motio выводит его из даты.

## Отсутствия

Для списка нужна область `read` или `time_off`; для создания, изменения и
удаления — `time_off`.

### Список отсутствий

```
GET /time-off?from=YYYY-MM-DD&to=YYYY-MM-DD
```

Оба фильтра необязательны и выбирают отсутствия, которые пересекаются с
диапазоном. Отдаются все отсутствия пространства, импортированные и нет (до 5000),
одним ответом: этот список на страницы не делится.

```bash
curl -s "https://planner.example.com/functions/v1/api/v1/time-off?from=2026-11-01&to=2026-11-30" \
  -H "Authorization: Bearer $MOTIO_TOKEN"
```

```json
{
  "items": [
    {
      "id": "3f0c7a52-…",
      "external_id": "hr-1042",
      "email": "anna@example.com",
      "person": "Anna Becker",
      "start_date": "2026-11-09",
      "end_date": "2026-11-13",
      "note": "Vacation",
      "updated_at": "2026-10-28T09:12:44.512000+00:00"
    }
  ]
}
```

`external_id` равен `null` у отсутствий, введённых вручную; `email` равен `null` у
людей без учётной записи и у тех, кто вышел из пространства.

### Создать или обновить отсутствия

```
PUT /time-off
```

`POST` делает то же самое. Тело: `{"items": [...]}` (подойдёт и просто массив).
Каждый элемент:

| Поле | Обязательно | |
|---|---|---|
| `external_id` | да | идентификатор в вашей системе |
| `email` | да | почта учётной записи человека в Motio |
| `start_date` | да | первый день отсутствия, `YYYY-MM-DD` |
| `end_date` | да | последний день отсутствия (включительно), не раньше `start_date` |
| `note` | нет | до 1000 символов, видна команде |

```bash
curl -s -X PUT "https://planner.example.com/functions/v1/api/v1/time-off" \
  -H "Authorization: Bearer $MOTIO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "items": [
      {"external_id": "hr-1042", "email": "anna@example.com",
       "start_date": "2026-11-09", "end_date": "2026-11-13", "note": "Vacation"},
      {"external_id": "hr-1043", "email": "max@example.com",
       "start_date": "2026-11-10", "end_date": "2026-11-10", "note": "Training"}
    ]
  }'
```

Каждый элемент обрабатывается отдельно и получает свой результат, в порядке
отправки. Плохой элемент никогда не блокирует остальные; сам запрос отвечает
`200`:

```json
{
  "summary": {"created": 1, "updated": 0, "unchanged": 0, "error": 1},
  "results": [
    {"external_id": "hr-1042", "status": "created", "id": "3f0c7a52-…"},
    {"external_id": "hr-1043", "status": "error", "error": "PERSON_NOT_FOUND"}
  ]
}
```

| `status` | Значение |
|---|---|
| `created` | новое отсутствие |
| `updated` | отсутствие с таким `external_id` было и изменилось |
| `unchanged` | оно было и уже совпадало |
| `error` | не сохранено; см. `error` |

| `error` | Значение |
|---|---|
| `INVALID_EXTERNAL_ID` | не указан, пуст или длиннее 200 символов |
| `INVALID_DATES` | не `YYYY-MM-DD`, несуществующая дата или конец раньше начала |
| `INVALID_NOTE` | заметка длиннее 1000 символов |
| `PERSON_NOT_FOUND` | в пространстве нет участника с такой почтой учётной записи |
| `OVERLAP` | у человека уже есть отсутствие в какие-то из этих дней |

Повторная отправка тех же данных безопасна: вы получите `unchanged`. Ночная
задача может каждый раз отправлять полный список предстоящих отсутствий.

### Удалить отсутствие

```
DELETE /time-off/{external_id}
```

```bash
curl -s -X DELETE "https://planner.example.com/functions/v1/api/v1/time-off/hr-1042" \
  -H "Authorization: Bearer $MOTIO_TOKEN"
```

`204`, если удалено; `404`, если импортированного отсутствия с таким
идентификатором нет. Идентификаторы с пробелами и другими особыми символами
кодируйте для адреса. Идентификатор, в котором есть `/`, в пути передать нельзя —
прокси его там раскодируют или отклонят, — поэтому передавайте его параметром:

```
DELETE /time-off?external_id=hr%2F1042
```

Удалять отсутствия, которые исчезли из вашей системы, должна вызывающая сторона:
получить список через `GET`, сравнить, удалить.

## Ошибки

У ошибок уровня запроса один вид:

```json
{"error": {"code": "unauthorized", "message": "unknown or revoked workspace token"}}
```

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `invalid_json` | тело не является JSON |
| 401 | `unauthorized` | токен не указан, неправильного вида, неизвестен или отозван |
| 403 | `forbidden` | у токена нет области, которая нужна этому методу |
| 404 | `not_found` | неизвестный адрес, нет такой задачи или нечего удалять |
| 405 | `method_not_allowed` | метод не подходит для этого адреса |
| 413 | `payload_too_large` | тело больше 256 КБ |
| 422 | `invalid_query` / `invalid_body` | неправильный фильтр, `limit` или `cursor` (несуществующая дата тоже считается); пустой или слишком большой `items` |
| 429 | — | лимит запросов; повторите через секунду |
| 500 | `internal_error` | проблема на нашей стороне; повторите позже |

## О безопасности

- Обращайтесь с токеном как с паролем: храните его в хранилище секретов и никогда
  — в репозитории или в браузере.
- Давайте токену только ту область, которая нужна системе: инструмент отчётов
  читает, синхронизация с HR импортирует отсутствия. Токен с областью `read` видит
  все задачи, описания и почты учётных записей пространства.
- По токену на систему — и отзывать будет легко. У каждого токена видно, когда им
  пользовались в последний раз.
- Создавать, видеть и отзывать токены могут только администраторы пространства.
  Токены хранятся в виде хешей SHA-256; дамп базы их не раскрывает.
- Всегда используйте `https://`. Запрос, отправленный на `http://`, несёт токен
  открытым текстом ещё до того, как сервер успеет перенаправить.
- Токен передаётся в заголовке `Authorization` и больше нигде. Токен в адресе
  (`?token=…`) не принимается и при этом оседает в журналах доступа каждого прокси
  по пути: если так случилось, отзовите его.
- Создание и отзыв токена записываются в историю пространства (**Участники и
  доступ → История**): кто это сделал, как называется токен и что он может.
- Запросы записываются в журнал сервера: пространство, действие, результат и
  короткий префикс токена (`motio_1a2b3c4d`, тот же, что показан в настройках), —
  так администратор сервера видит, какая программа делала запрос. Сам токен, почты
  и отданные данные в журнал не попадают никогда.
